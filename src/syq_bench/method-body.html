How we measure

Every chart starts with a described job, an actual run, and measurements you can inspect.

Recorded runs, generated files

The published performance results come from actual transfers of generated test files, not simulated timings or display placeholders. Speeds and ratios are calculated from the captured times. Download each run to inspect its measurements, verification results and setup. Cloud cost estimates are estimates, not measured bills.

Time the whole command

The clock starts when the copy tool starts and stops when it exits. Startup, connection setup and finishing work count. Fixture creation and checksum verification are outside that clock. Where enabled, the harness measures a separate post-copy flush; that time appears beside each repeat. A missing flush is not a zero-cost durable write. The Fly WAN scenarios use tmpfs and deliberately do not measure persistent storage.

Compare one run at a time

Tools run in interleaved order against the same fixture. The main charts use the latest selected run of each scenario. Older runs remain visible separately. We do not combine unknown remote identities, independent allocations, or different builds into a single measurement. A development version string can describe several commits; consult the source revision and binary hashes, not just the version label.

Read the bars

Every chart shows effective speed: the reference dataset size divided by mean command time. Longer bars are always better. We use the same calculation for a new copy and an update to an existing copy.

For an update, a tool can reuse unchanged data instead of sending it again. A higher effective speed means it completes the same job faster—not that it sends more bytes per second. The reference size is the recorded fixture size before edits, including for tests that append data. Neither that size nor the logical changed-byte count measures network traffic. Compare tools within the same test; a small edit and a complete copy are different jobs.

Whiskers show the speeds calculated from the slowest and fastest observed repeats, not a confidence interval. One repeat has no whisker. Raw elapsed times remain available under “Inspect all repeats”. Sizes and rates use decimal units: 1 MB = 1,000,000 bytes and 1 GB = 1,000 MB. Displayed values are rounded; downloads preserve the recorded precision.

Read the comparison

The quickest valid result is “fastest measured”. A tool within 5%, or within 15% with overlapping repeat ranges, is marked comparable. Other labels give a percentage of the fastest effective speed in that chart. This is a display heuristic, not a significance test. Under-two-second measurements are marked; when all results are that short, we do not rank them. Failed, unverified, aborted, or improperly prepared cases receive no performance bar. Their recorded repeats remain available. Default syq is selected explicitly by the scenario; tuned variants appear in the controls, not as competitors.

Know what was controlled

A fresh copy uses an empty harness-owned destination. An incremental run first seeds the destination, modifies the source, then times the re-sync. The recipe states the cache policy: warm does not evict pages; evict requests eviction of fixture pages only. Metadata and server caches can remain warm. The data records which cache preparation actually succeeded. The performance tools themselves and the cloud network remain subject to ambient load.

Why the update experiment has a full-rewrite control

The small-edit and full-rewrite cases use the same file sizes, connection and protocol. The difference is what changes: small pieces or all the contents. This tests whether reusing old data helps. A full rewrite resembles a fresh transfer, but the destination already has files to inspect and replace; it is not the same procedure as copying into an empty destination. The other remote-copy sections also use different file sizes and counts, so their rates are not duplicate measurements of this control.

How to read the explanations

“The controls show” points to a measured comparison with a syq variant. “Likely reason” is an interpretation of the recorded behavior, not an isolated proof of the cause. “Not yet explained” means these measurements do not establish the reason. Explanations are tied to the specific captures reviewed; a changed result or build needs a new interpretation.

Which data path did syq use?

Each syq bar names its data path. “Observed” means the saved data-connection diagnostics record TCP, SSH, or both; a successful reachability probe alone does not qualify. “Requested” describes a command setting, not an observed connection. “Unrecorded” means the saved run cannot establish the actual path; the default TCP setting is not proof that SSH fallback did not occur. A partial record means some repeats have evidence and others do not. Inspect the repeat table for the individual records.

“Local copy” means both endpoints are on the computer running syq. Internal receiver communication can still use TCP; this does not imply traffic crosses the physical network. An NFS mount still sends storage traffic over the network. syq can use kernel-side copying such as copy_file_range where supported, but these runs do not record which local copy optimization was used.

The update explanation uses rsync’s documented delta-transfer behavior and the tested syq implementation. It does not claim that actual network bytes were recorded.

Reproduce the experiment

Reproduction means following the same described procedure with your own resources. Different allocations and different days will produce different numbers. The useful question is whether the relative behavior and its mechanism persist. Start with the published recipe, then inspect the transport, capacity probes and workload shape if your result differs. Do not resize the workload so far that it stops exercising the feature being measured.

Know what is missing

An older collector sometimes failed to record the binary actually selected at the remote end. Affected identities are marked unrecorded; a matching local version does not establish a matching remote build. Consult each run’s identity table. The published WAN recipe compares rsync; it has no qcp or tar entry. The public local-storage cases include a manual rental recipe. Private hardware sections remain where the public comparisons do not reproduce their larger benefits or have no matching case. Hardware, build, file size and cache differences prevent treating them as interchangeable measurements.
