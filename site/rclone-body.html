How to read the results

Speeds are dataset bytes divided by mean command time, using decimal MB/s and GB/s, just like the main benchmark page. Seconds remain visible. The thin line shows the observed speed range when multiple runs exist; individual times and speeds are directly below each command. This is effective copy throughput, including startup and native checksum work—not a measurement of wire speed or durable storage bandwidth.

These are old screening measurements used to preview the layout. They have not been replaced by the longer campaign yet. The publication campaign will use three successful, verified runs per tool and setting, with rotated order. We will calibrate workload size so the fastest tool runs for at least 10 seconds as a starting target; WAN payload work must also clearly outweigh measured startup. A duration threshold alone cannot prove that overhead is negligible.

Short or incomplete cases are marked beside the bars. Existing timings remain inspectable; they are not relabelled as results of larger datasets. The final comparisons need new measurements and a review of cache, metadata, authentication and rail controls before publication.

“Local filesystem” includes mounted NFS. Both programs access normal paths; the operating system’s NFS client talks to the NFS server. No SFTP or WebDAV service is involved in those tests. For server-to-server copies we tested rclone’s SFTP and HTTPS/WebDAV backends separately. See rclone’s local backend documentation.

Copy speeds, commands and datasets

Try a copy without the benchmark harness

The following is an inspectable Linux recipe for a filesystem copy, including mounted NFS. Use Python 3.9+, Bash, GNU time and coreutils, plus the listed syq/rclone versions. Download make-files.py next to your shell session. The generator writes seeded pseudorandom bytes, not sparse or all-zero files, checks available space, and refuses an existing source directory. It changes no system settings and removes nothing.

This is a proposed simpler recipe for the replacement campaign. It matches the specified file counts, sizes and directory layout, but uses a different byte generator and buffered preparation. It did not produce the screening numbers above. We must record its actual cache state and metadata checks when collecting the replacement measurements.

1. Create one dataset and inspect it

set -euo pipefail
# Choose existing scratch parents on the filesystems being compared.
SOURCE_PARENT=/path/to/source/scratch
DEST_PARENT=/path/to/destination/scratch
CASE=$(mktemp -d "$SOURCE_PARENT/rclone-comparison.XXXXXX")
SRC="$CASE/source"
python3 make-files.py "$SRC" --files 40000 --size 4096 --directories 256 --seed 9911
find "$SRC" -type f | wc -l
du --apparent-size --bytes --summarize "$SRC"
(cd "$SRC" && find . -type f -print0 | LC_ALL=C sort -z | xargs -0 sha256sum) > "$CASE/source.sha256"

Use the count, size and directory arguments printed beside the desired case above. The file sizes sum to the payload; du also counts directory entries. For longer tests, increase file count while retaining 4 KiB files, or increase bytes per large file while retaining the intended file count. Calibrate against the fastest tool, then freeze the same dataset for all three runs of every setting.

2. Prepare cache state outside the timer

This requests eviction of source file pages only. It cannot evict NFS server caches or metadata caches; tmpfs remains memory-resident. Source flushing below is preparation, not a destination durability flush. If eviction fails, record the failure instead of calling the test cold. Run this before every timed copy:

python3 - "$SRC" <<'PY'
import os, pathlib, sys
for p in pathlib.Path(sys.argv[1]).rglob('*'):
    if p.is_file():
        with p.open('rb') as f:
            os.fsync(f.fileno())
            os.posix_fadvise(f.fileno(), 0, 0, os.POSIX_FADV_DONTNEED)
print('Source eviction requested; metadata and server cache remain uncontrolled.')
PY

3. Run one exact command into a fresh destination

# Check free bytes AND inodes before each copy; allow room for all retained runs.
df -B1 "$DEST_PARENT"
df -i "$DEST_PARENT"
DST=$(mktemp -d "$DEST_PARENT/rclone-copy.XXXXXX")
RUN=1                 # Use 1, 2, 3; retain a separate time file for each setting/run.
LABEL=rclone-t64
/usr/bin/time -f 'elapsed_seconds=%e exit_status=%x' -o "$CASE/$LABEL-r$RUN.time"   rclone copy --config /dev/null --metadata --create-empty-src-dirs   --transfers 64 -- "$SRC" "$DST"

Check the command’s exit status before using its timing. For syq, allocate another fresh destination, repeat the cache preparation and time syq rsync -a --no-progress "$SRC/" "$DST". For another rclone setting, substitute the exact flags printed beside its result. Do not copy over a previous destination: that would measure an update instead of a new copy.

4. Check contents after timing

(cd "$DST" && sha256sum --check "$CASE/source.sha256")
# Also check that there are no unexpected files.
(cd "$SRC" && find . -type f -print0 | LC_ALL=C sort -z) > "$CASE/source-files"
(cd "$DST" && find . -type f -print0 | LC_ALL=C sort -z) > "$CASE/destination-files"
cmp "$CASE/source-files" "$CASE/destination-files"

This checks file names and contents. For filesystem copies, compare metadata separately (excluding the root, whose permissions come from mktemp):

python3 - "$SRC" "$DST" <<'PY'
import pathlib, sys
def metadata(root):
    return {str(p.relative_to(root)): (s.st_mode, s.st_uid, s.st_gid, s.st_mtime_ns)
            for p in root.rglob('*') for s in [p.lstat()]}
a, b = (metadata(pathlib.Path(p)) for p in sys.argv[1:])
if a != b:
    raise SystemExit('Metadata mismatch: do not count this as a verified copy')
print('File/directory types, modes, numeric ownership and mtimes match.')
PY

This covers the regular-file/directory fixtures here, not ACLs, extended attributes, hard links or symlinks. Network tests used the narrower metadata check of regular-file mtimes to whole seconds; do not apply the filesystem check to SFTP/WebDAV and assume they promise archive-equivalent preservation.

Repeat the prepare → fresh destination → timed command → verification sequence three times per setting, rotating tool order each round. Retain each time and exit status. Do not include generation, cache preparation, verification or cleanup in elapsed copy time. These commands leave generated directories in place for inspection; remove only the scratch trees you created when finished.

For SFTP and WebDAV

Generate the same source dataset locally, create a fresh scratch destination on the receiving filesystem, and use the exact network command shown beside the result. Replace SOURCE, DESTINATION, SERVER, PORT, USER, KEY_FILE and KNOWN_HOSTS with the selected paths and SSH settings. SFTP needs the existing SSH/SFTP service; the measured client used rclone’s built-in SSH implementation. Use a local key for same-data-center tests so WAN-forwarded signing does not distort them.

The measured WebDAV server command, with private values replaced, was:

rclone serve webdav "$REMOTE_SCRATCH" --config /dev/null   --addr SERVER:PORT --dir-cache-time 0s --cert CERT_FILE --key TLS_KEY_FILE

Server authentication was provided by RCLONE_USER and RCLONE_PASS in the environment; clients used RCLONE_WEBDAV_USER and rclone-obscured RCLONE_WEBDAV_PASS. The client URL is HTTPS, with --webdav-vendor rclone --ca-cert CA_CERT. Start a listener only on your authorized server and scratch root, and stop it when finished. Check free space and perform content/metadata verification on the receiving host outside the timed client command. These endpoint steps depend on your server; the local recipe alone is not a complete network reproduction.

Settings and server setup

Every rclone command used copy --config /dev/null --create-empty-src-dirs. Filesystem copies added --metadata. Network copies did not request archive-equivalent metadata: we checked regular-file contents and mtimes to whole seconds, not ownership, modes, ACLs or extended attributes.

SFTP used rclone’s built-in SSH implementation against the existing SSH/SFTP service, with host-key verification. Corrected LAN and fast-fabric tests used a local private key. Earlier LAN tests used an agent forwarded over the WAN; the authentication delay affected both tools, and those trials are retained only in the appendix. WAN tests used agent authentication.

WebDAV used rclone serve webdav with HTTPS, authentication and server-side --dir-cache-time 0s. The client used --webdav-vendor rclone and a verified TLS certificate. Thus these results describe this particular WebDAV server as well as the client.

We varied --transfers, --multi-thread-streams, --sftp-chunk-size, --sftp-concurrency and --webdav-pacer-min-sleep. Exact values appear in each row and its command disclosure. We kept default hashing enabled and did not sweep checkers, buffer sizes, connection limits or hash options.

Network screening generally used --contimeout 5s --retries 1. Some early tests also used --timeout 15s; this interrupted hashing on the large SFTP test, so the corrected fast-fabric test restored the normal IO timeout. Those failed attempts remain in the appendix. Zero WebDAV pacing failed concurrent directory creation on one small-file LAN test; a 2 ms follow-up timed out.

syq filesystem copies used rsync -a --no-progress. Network copies used rsync -rt --no-progress --syq-no-bootstrap with an already installed remote binary; automatic transport and worker selection remained enabled. WAN logs recorded direct TCP, not SSH fallback. We did not sweep syq worker counts or congestion control. “Automatic” does not mean we established optimal tuning.

Would using all eight network rails help rclone?

The fast hosts have eight network interfaces rated at 400 Gb/s each, with separate rail addresses. syq selected eight destination addresses automatically; our rclone commands selected one. We have not measured rclone across all eight rails, or syq restricted to the same single rail.

Rclone documents one outgoing address for --bind and one SFTP host per remote. We have not found a documented automatic equivalent to syq’s rail discovery in this setup. A practical candidate is to partition the file list into eight disjoint sets and run eight rclone processes, each targeting a different rail (with source binding where needed). Time the whole group, check every exit status, and verify the combined destination. That is an untested configuration, and it would not stripe a single file.

The rail difference does not establish the cause of the speed gap. One 400 Gb/s rail has a nominal capacity of 50 GB/s before protocol overhead—already well above the rclone throughput observed here. Hashing, CPU work, file parallelism, the server implementation and load could matter. We need matched single-rail controls and the multi-process experiment before attributing the difference to a rail limitation.

If you know a better rclone setup for these hosts or workloads, please suggest it in the discussion. We want the comparison to give both tools a fair chance.

What was controlled, and what was not

Fixtures and destination trees were generated for the benchmark. Each timed copy was followed by independent content verification outside timing. The filesystem cases also checked types, modes, numeric ownership and mtimes; network metadata checks covered regular-file mtimes to whole seconds. This is not a test of interrupted-copy recovery, atomic replacement, archive fidelity or crash durability.

The download contains individual timings, exit status, verification fields, workload size, seed, protocol and commands with endpoint placeholders. It preserves failed and unfavorable trials as well as successful copies. Private operational logs are not public. The experimental rclone harness adapters have not yet been released, so the existing data are not yet a complete independently reproducible benchmark package. The small standalone recipe above makes the replacement procedure inspectable without those adapters.

The separate syq/rsync benchmark page has a different measurement protocol. Do not combine numbers across the two pages as if they came from the same campaign.
