How the copies were measured

Each tool copied generated pseudorandom files into an empty destination. Elapsed time includes connection setup and the tool’s own checksumming, but excludes dataset preparation, independent verification and cleanup. Completion does not include a final durability flush.

WAN sources stayed in memory (tmpfs); destinations were on XFS RAID. File contents, sizes and whole-second modification times were checked after every copy. Filesystem comparisons additionally checked types, permissions, ownership and directory times. These tests do not measure interrupted-copy recovery or full archive preservation.

WAN tool order rotated between runs. One WebDAV run overlapped unrelated local work and was replaced. syq used automatic worker selection with its existing tuning cache, which changed worker counts between runs. NFS server caches and other clients were uncontrolled. The fast-fabric receiver was busy; its short transfers do not establish peak throughput.

Datasets are described beside each chart. The optional dataset generator can recreate their file counts, sizes and layout; it was not the harness used to collect these measurements. The JSON includes individual timings, verification scope, commands and tool hashes. The experimental measurement harness has not been released publicly.

Transfer settings

Rclone’s --transfers controls concurrent files, not streams within one file. Settings were selected from trials of transfer counts, SFTP packet sizes and request concurrency, SSH connection sharing and WebDAV pacing. They are the best configurations among those tested, not a claim of optimal settings for every system.

SFTP used the existing SSH service with host-key verification. WebDAV used an authenticated rclone serve webdav server over HTTPS with a verified certificate. Services and remote binaries were prepared before timing; starting each copy’s connections remained timed. WAN SSH authentication used a local key. File mtimes were preserved; SFTP and WebDAV were not asked to preserve Unix ownership, permissions or ACLs.

The WebDAV server received RCLONE_USER and RCLONE_PASS through its environment; the client used RCLONE_WEBDAV_USER and rclone-obscured RCLONE_WEBDAV_PASS. The copy commands above include the remaining client settings.

Multi-rail networking

In these tests, syq used eight rail addresses; rclone used one. Increasing --transfers creates concurrent file transfers to the configured endpoint; it does not distribute them across the eight separate addresses.

For rclone 1.75.1 uploads, SFTP keeps one connection per file, with concurrent requests on that connection. The WebDAV server configuration tested here uploads each file in one request. Neither stripes a single upload across these rails. Multiple files could be divided among separate rclone processes targeting different rail addresses; that configuration was not tested.

This is not a universal one-file limit: rclone supports multithread transfers for capable destinations, including downloads to local storage. Using multiple physical links also depends on routing and network configuration; multiple streams alone do not select separate rail addresses.

Each rail is rated at 400 Gb/s (50 GB/s), already above the measured speeds here. Unequal rail use, receiver load and short durations prevent attributing the speed difference to rail count. That per-rail rating is not a measured end-to-end copy limit.

Suggestions for improving either tool’s settings are welcome in the discussion.
